# BIBAS — CRM ювелирной мастерской

Первая рабочая версия для одной организации: клиенты, ремонт и изготовление,
карточки изделий, мастер и срок, поиск, просроченные заказы, история статусов,
оплаты и возвраты. Интерфейс на русском, адаптивный.

Цель — около 50 сотрудников. Это ориентир архитектуры, а не результат
нагрузочного теста. PostgreSQL обязателен для облачной эксплуатации;
SQLite используется только для локального знакомства и быстрых тестов.

## Локальный запуск (PowerShell)

Python 3.13:
```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
$env:DJANGO_DEBUG="1"
python manage.py migrate
python manage.py setup_roles
python manage.py createsuperuser
python manage.py runserver 127.0.0.1:8000
```

Открыть http://127.0.0.1:8000. Учётных записей и паролей по умолчанию нет.
Администратор создаёт сотрудников в /admin/ и назначает группы.
Обычным сотрудникам не нужен is_staff. Права на управление пользователями
выдаёт только владелец мастерской.

## Роли

- Приёмщик: клиенты, создание заказов, просмотр и смена статуса.
- Мастер: просмотр всех заказов, включая контакт клиента и расчёты, смена статуса.
- Кассир: просмотр всех заказов, оплаты и возвраты.
- Администратор (superuser): все действия и управление учётными записями.

Группы можно комбинировать. setup_roles повторно устанавливает стандартные
права этих трёх групп. Доступ к заказам общий внутри организации;
ограничения «только мои заказы» и несколько организаций пока не реализованы.

## Правила данных

Суммы — Decimal с двумя знаками после запятой (точность до копейки), не float.
Номер заказа — первичный ключ базы. Повторный POST не создаёт второй заказ
благодаря уникальному идентификатору создания. Оплата имеет отдельный уникальный
идентификатор; повтор не создаёт вторую операцию.
Возврат не может превышать полученную сумму, оплата — остаток.
Для закрытого заказа разрешён возврат, но не новая оплата.
Выдача изделия разрешена только при нулевом остатке долга. Проверка выполняется
в транзакции под той же блокировкой заказа, что и финансовые операции.
Возврат до выдачи снова создаёт долг и блокирует выдачу до доплаты.
Возвраты после выдачи остаются отдельными финансовыми операциями.

Повтор создания заказа с тем же идентификатором и теми же проверенными полями
возвращает прежний заказ. Изменённые данные или другой автор дают HTTP 409;
форма сохраняет введённые значения, существующий заказ не изменяется.
Для создания другого заказа нужно открыть новую форму с новым идентификатором.

Переходы: принят → согласование/в работе/отменён;
согласование → в работе/отменён; в работе → согласование/готов/отменён;
готов → в работе/выдан/отменён. Выдан и отменён — конечные состояния.

История и финансовые записи не редактируются и не удаляются через UI.
Неверный платёж корректируется возвратом. Транзакции блокируют заказ на
PostgreSQL; конфликт смены статуса требует обновить страницу.
Администратор базы технически может изменить записи:
это операционный журнал, не криптографически защищённый аудит.

## Облако

См. [docs/deployment.md](docs/deployment.md). Docker Compose включает PostgreSQL
и Gunicorn, порт приложения доступен только через loopback.
Production требует секрет и PostgreSQL, включает HTTPS redirect, secure cookies и HSTS.

## Проверки

```powershell
$env:DJANGO_DEBUG="1"
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py collectstatic --noinput
python manage.py test
```

GitHub Actions настроен для PostgreSQL 17, включая конкурентную оплату.
Локальная SQLite пропускает этот тест: SELECT FOR UPDATE не поддерживается.

## Контроль мастерской и библиотека

Добавлены контроль просрочек и активности, фиксация согласования цены, учёт
золота, библиотека вариантов изделий и опциональный AI-конструктор.
Подробности, ограничения и обновление: [docs/workshop.md](docs/workshop.md).

## Границы первой версии

Пока нет загрузки фото, печатной квитанции, редактирования принятого заказа,
фискализации, внешних уведомлений, MFA, восстановления пароля по email,
автоматического резервного копирования и защиты входа от перебора на уровне приложения.
Перед реальной работой нужны защита входа на reverse proxy/identity gateway,
резервные копии с проверкой восстановления и нагрузочное тестирование.
Не загружайте реальные персональные данные до завершения этих настроек.
